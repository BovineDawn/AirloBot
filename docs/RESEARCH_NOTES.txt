GROK BOT RESEARCH NOTES | 2026-11-01

Primary public documentation
- https://docs.x.ai/grok-bot/bots
  Named Bots have jobs and ongoing context; a primary Bot coordinates others.
- https://docs.x.ai/grok-bot/chat-and-collaboration
  Work is visible through activity, results and handoffs. Keep ownership clear
  and avoid helpers duplicating each other's work.
- https://docs.x.ai/grok-bot/overview
  Grok Bot uses a persistent cloud computer. This is a deployment difference
  from AirloBot's proposed local worker, not something achieved by UI cloning.
- https://docs.x.ai/grok-bot/computer-and-apps
  Bots share computer resources. Per-bot context/screens are not security isolation.
- https://docs.x.ai/grok-bot/approvals-security-and-privacy
  Approval interactions expose concrete actions. AirloBot should enforce these
  in host code rather than relying on a model instruction to ask nicely.
- https://docs.x.ai/grok-bot/skills-routines-and-automations
  Reusable instructions and scheduled workflows follow successful one-off tasks.
- https://lmstudio.ai/docs/developer/openai-compat/tools
  The model requests functions; the host executes them and returns results.
  Support and output format vary with the model and its runtime/template.
- https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture
  MCP supplies tools/context through host/client/server components. Local stdio
  can be useful later but does not replace our agent/task scheduler.

Local research cross-check (kept outside this public Git repository)
The parent grokbotclone reports describe task/subagent UI, automation and bot
management surfaces, and gateway declarations for createAgent, getSubagents,
getAsyncTasks, getAgentTasks and interruptAgentRun. These are client-facing
contracts and static evidence, not recovered server orchestration code or proof
that any particular model implements delegation internally.

AirloBot code audit
The current service streams /v1/chat/completions from fixed loopback, stores
conversations in JSON and allows one generation at a time. It does not send
tools, process tool_calls or execute agent tasks. HF downloads already pin a
revision and verify size/SHA-256 before importing into the local runtime.

Our inference and design choice
Grok Bot's ease of use can be approximated by clear ownership, durable jobs,
visible work and bounded delegation. A large cloud model is not required for
the orchestration mechanism. Whether the installed small model completes tasks
reliably must be measured; a scheduler alone cannot supply reasoning capability.
See AGENT_ROADMAP.txt for the proposed order and acceptance criteria.

Provenance boundary
AirloBot is an independent implementation. This repository excludes original
Grok Bot binaries, extracted source, proprietary artwork, credentials, private
conversations and model weights. Research notes distinguish public product
behavior, local observations and our proposed implementation.
